# 💥 翻车案例集（Failure Cases）

> 每个案例：现象 → 当时的误判 → 根因 → 修复法 → 通用教训。全部来自一个生产 agent（2026-08~11）的真实运行记录，机制描述公开、无敏感信息。**共同主题：故障几乎都是「静默」的——不报错，甚至探活全绿。**

## 案例 1：模型路由静默降级

- **现象**：某天起所有回复质量无异常，但计费变高。
- **误判**：探活检查全绿 → 判定「路由配置正常」，差点就此打住。
- **根因**：配置里 provider 名写了一个未注册的名字。Hermes 对未注册 provider 不报错，而是**每条消息静默 fallback 到备胎模型**，探活探测的是备胎（当然绿）。
- **修复法**：验收路由配置改为查**真实计费记录**（billing provider 字段），探活只作辅助信号。
- **通用教训**：🟢 灯绿 ≠ 事情对了。任何「配置生效」的验收必须看副作用侧的真实数据（账单、日志、产物），不能只看连通性探测。

## 案例 2：记忆服务静默挂死

- **现象**：模型开始忘记长期事实，但没有任何报错。
- **误判**：先怀疑模型本身「变笨了」。
- **根因**：上游工具链升级更换了 Python 解释器（3.14.7→3.14.9），删除旧解释器目录导致记忆服务的 venv 断链——进程没了，但调用方把「取不到记忆」当「没有相关记忆」正常处理。
- **修复法**：用新解释器重建 venv + 数据完好性确认 + 把「记忆服务探活」加入每日巡检。
- **通用教训**：记忆是基建，基建也会塌。**任何「检索为空」的路径都必须区分「真没有」和「查不了」**——后者要显式报警而不是静默降级。

## 案例 3：数据源冻结一年不报错

- **现象**：宏观经济数据正常推送，用户照常引用。
- **误判**：无（这是抽查时发现的，此前无任何告警）。
- **根因**：某上游数据源接口停止更新（最新数据停在一年前），但接口不返回错误，管线「成功」地推送了一年前的旧数据。
- **修复法**：所有数据源加时效判据——**最新一期日期距今天数 > 阈值即视为失效，宁可不报**。
- **通用教训**：「不报错」≠「还在工作」。只增不改的外部数据源必须验活（最新日期检查），这是所有时效类推送管线的前置门。

## 案例 4：命令被「翻译」导致垃圾直投

- **现象**：用户某天收到一行乱码 token 而不是预期的静默（正常情况下「成功=不推送」）。
- **误判**：无（周度偏误体检抓到的）。
- **根因**：cron prompt 要求成功时回复 ASCII 标记 `[SILENT]`，某次模型把它翻译成了中文「[无声]」——系统识别不到标记，把「成功回复」当正文原样投递给了用户。
- **修复法**：prompt 中明确「必须逐字符复制 ASCII [SILENT]，禁止翻译」，并考虑在识别侧做宽松匹配兜底。
- **通用教训**：**给模型的机器协议标记要做翻译免疫**（说明「这是协议不是语言」），识别侧对标记做归一化匹配。靠一个脆弱字符串做控制流 = 等着被 LLM 的「翻译本能」打断。

## 案例 5：进化器对已归档技能空转一周

- **现象**：每周进化任务报告 holdout 提升 +7.3%，看似健康。
- **误判**：第一眼当成了真实进化（+0.047 的提升在报告里很显眼）。
- **根因**：双重叠假——①进化目标技能其实已被移入归档目录（管线在优化一个不存在的技能）；②evolved 与 baseline 逐字节相同，提升来自优化器内部参数扰动，在评测噪声范围内（holdout 仅 5 样本）。
- **修复法**：进化循环加前置检查（目标技能存在且在位）；进化声明必须 diff 为空检测 + holdout 样本量门槛；下轮换有效目标。
- **通用教训**：**进化/自改进系统最擅长「假装进步」**。任何「提升了 X%」的报告必须先过三问：目标还活着吗？产物真的变了吗？提升超过评测噪声吗？（与 K3「满分即作弊」同源。）

## 案例 6：空快照会误删整棵依赖树

- **现象**：无（安全审计中发现的设计缺陷，未上线即修）。
- **误判**：无。
- **根因**：某「安装前快照→失败回滚」的安全机制，当快照本身失败（返回空）时，回滚逻辑把「空快照」当「原始状态」，会把刚安装的整棵依赖树删掉——安全机制本身成了破坏者。
- **修复法**：快照失败 = ABORT，禁止回滚；回滚操作必须有「快照非空」前置断言。
- **通用教训**：**安全机制的失败路径比功能路径更危险**。每个「失败时执行 X」的分支都要问：X 在异常输入下会造成什么？

## 案例 7：时间戳可伪造的完整性检查

- **现象**：无（红队复审发现）。
- **误判**：原检查逻辑用文件 mtime 判断「产物是否新鲜」，看似合理。
- **根因**：mtime 可以用 `touch` 任意伪造——检查给了「被审计者自己伪造证据通过审计」的能力。
- **修复法**：改为断言**内容字段**（文件内必须有当日实际数据特征），不依赖可伪造的元数据。
- **通用教训**：完整性检查的输入必须是**不可伪造的内容特征**，不是可伪造的元数据（时间戳/文件名/大小同理）。

## 案例 8：域名白名单的后缀绕过

- **现象**：无（安全加固时发现）。
- **误判**：白名单用 `host.endswith("gov.cn")` 判断，看似严密。
- **根因**：`evilgov.cn` 同样 endswith `gov.cn`——后缀匹配放行了完全无关的恶意域名。
- **修复法**：精确后缀匹配（`.gov.cn` 带点）或域名集合匹配 + 解析 IP 必须 is_global + 重定向逐跳校验。
- **通用教训**：**字符串白名单是安全玻璃不是保险箱**。每个匹配规则都要构造一个「想绕过它的人会怎么写域名」的反例来测试。

## 案例 9：评估脚本吞错，坏结论存活 41 天

- **现象**：某外部命令（sqlite3 CLI）实际已损坏，配合脚本 `2>/dev/null` 吞掉了错误输出，依赖它的下游判定一切正常。
- **误判**：损坏后近一个月内无告警；发现前的排查都停在「下游逻辑」层面。
- **根因**：双重掩盖——库文件被劫持导致 symbol lookup error + 脚本把 stderr 丢掉。错误信号在第一跳就被消灭。
- **修复法**：全系统约定禁用盲目 `2>/dev/null`；「某功能最近才坏」的排查第一步永远是**裸跑外部命令本身**。
- **通用教训**：错误信息的传递链路上每一跳都可能吞掉它。诊断顺序：先验最底层的外部依赖，再看上层逻辑——不是反过来。

## 📌 跨案例模式总结

| 模式 | 案例 | 一句话防御 |
|---|---|---|
| 静默失败（不报错型故障） | 1/2/3/9 | 空结果与查不了的区分 + 真实副作用验收 |
| LLM 行为不可假设 | 4 | 机器协议标记做翻译免疫 |
| 自评自改的可欺骗性 | 5 | 目标存活检查 + diff 非空 + 噪声门槛 |
| 安全机制的失败路径 | 6/7/8 | 每个异常分支构造攻击者视角反例 |
